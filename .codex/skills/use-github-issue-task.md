# Skill: работа Codex через GitHub Issue

## Когда использовать

Используй этот skill, когда пользователь просит:
- выполнить задачу из GitHub Issue;
- оформить задачу для Codex через issue;
- продолжить работу по issue;
- оставить отчет в issue;
- связать Codex-задачу с branch / commit / PR.

## Назначение

GitHub Issue — основной контейнер задачи для Codex.

Цель workflow:
- уменьшить prompt-context в чате;
- зафиксировать задачу в git-traceable месте;
- отделить постановку задачи от исполнения;
- связать результат с branch / commit / PR / комментариями issue.

Task routing не хранится в этом skill.

Для выбора минимального task-route использовать:

```text
.codex/index.md
```

GitHub operations:

```text
.codex/skills/github-operations.md
```

## Canonical issue template

Основной шаблон задачи:

```text
.github/ISSUE_TEMPLATE/codex-task.md
```

При создании новой Codex-задачи использовать именно этот template.

Если issue создан вручную и не соответствует template:
- не переписывать issue целиком автоматически;
- использовать существующий контекст;
- при необходимости явно перечислить, каких секций не хватает.

## Правила чтения контекста

При работе по issue:

1. Сначала прочитать само issue полностью.
2. Затем прочитать только файлы из раздела `Контекст`.
3. Использовать `.codex/index.md` для выбора минимального route.
4. Не читать весь репозиторий без необходимости.
5. Если нужен дополнительный файл, открыть его только после краткой причины в рабочем отчете.

## Выполнение задачи из issue

Использовать:

```text
.codex/skills/github-operations.md
```

## Если issue неполный

Если issue не содержит достаточного контекста:

- не читать весь репозиторий вслепую;
- использовать `.codex/index.md` для выбора минимального route;
- явно перечислить, какого контекста не хватает;
- сделать best-effort только в безопасных границах.

## Запреты

- Не использовать issue как повод перечитать весь проект.
- Не смешивать несколько независимых задач в одном issue-commit.
- Не делать destructive git commands без явного запроса.
- Не закрывать issue, если Definition of Done не выполнен.
- Не скрывать пропущенные проверки.
- Не менять XML/business rules ради оформления workflow.
